Chapter 14

Judges' questions & answers

38 likely questions in 8 categories. Say = short confident answer · Deeper = follow-up detail · Don't claim = what would be untrue.

Answering techniqueAnswer in one sentence first, then offer detail: "Short answer: … If you like, I can show it." If you don't know: "We haven't measured that yet — it's a good next step." Never guess a number.

1Basic project questions

Q1What is EvacPrint, in one line?
SayA browser-based crowd-evacuation simulator that measures how long a venue takes to evacuate, finds where crowds jam, and tests which layout change gets people out fastest.
DeeperAgent-based model on a 0.5 m grid with Dijkstra routing, Weidmann speed–density, SFPE door capacity, Fruin density levels; recommendation engine with 3-seed re-simulation.
Don't claimThat it is a certified safety tool or a real-time emergency guidance system.
Q2Who would use it?
SayCollege and school administrators, event organisers, fire-safety officers preparing drills, and architects comparing layouts — anyone deciding door widths, seating or crowd limits.
Don't claimThat any institution is already using it.
Q3Is your Hall 406 model the exact real hall?
SayIt is a representative planning model — 21 × 15 m, 340 seats, three 1 m doors — built for the demo. The app itself says "verify dimensions on site before relying on absolute times".
DeeperWith a measured plan, the Venue Studio can rebuild it exactly: import the plan, calibrate with one known length, trace, add doors.
Don't claimThat we measured the real hall or that 93.6 s is the real evacuation time of Room 406.
Q4What does the user get at the end?
SayEvacuation time, 95 % time, peak density, bottleneck locations, exit usage, risk findings, ranked recommendations with before/after, and a printable report.

2Technical architecture

Q5What is your tech stack?
SayVanilla JavaScript with Vite; our own simulation engine; Three.js for 3D; Canvas 2D for the plan and heatmap; SVG charts; Web Workers for parallel runs; IndexedDB and localStorage for storage; a small Node.js server for the AI, which uses Google Gemini.
Don't claimReact, TypeScript, Python, a cloud database, or a model we trained.
Q6Do you have a backend and a database?
SayThe simulation runs entirely in the browser. The only server code is a Node.js layer that keeps the AI key secret and talks to Gemini. Data is stored in the browser — IndexedDB for venues and photos, localStorage for demo accounts and reports.
DeeperThat makes it fast, private and offline-capable; a production version would add a server database for sharing venues across devices and users.
Q7Why not React or another framework?
SayMost of the work is in canvas, WebGL and the engine, not in forms. Plain modules kept it fast and small, and the engine has no DOM dependency so it runs in Workers and Node unchanged.
Q8How do the 2D, 3D and charts stay in sync?
SayThey all read one shared simulation instance owned by a controller. There is no separate 3D simulation — the 3D layer only draws what the engine computes.
Q9What about privacy and security?
SayVenue data never leaves the browser unless the user chooses AI drafting. Demo passwords are hashed with PBKDF2 (210,000 iterations). The AI key is only on the server.
Don't claimProduction-grade authentication — the UI labels it "Demo authentication".

3Algorithm & simulation

Q10How is your simulation different from a normal animation?
SayAn animation is drawn in advance. Ours computes every person's position every 0.1 s from rules. Change any input — block a door, add people — and the result and the timings change. I can block a door right now and you'll see a different number.
DeeperReproducible: the same seed gives identical results, verified by our Node regression script (93.6 / 110.5 / 164.9 / 113.9 s).
Q11How do you calculate evacuation time?
SayWe don't use a formula — we measure it. Each agent's exit time is logged when they cross a final exit; RSET is the last one. We also report when 50 % and 95 % were out.
DeeperIt includes reaction time, walking, queuing and route changes. If anyone is still inside at 600 s the run is marked incomplete rather than giving a false number.
Q12How do you model human movement?
SayEach person walks down a distance map to their chosen exit at their own speed, slows down as local density rises (Weidmann curve), accelerates smoothly, can't overlap others or walls, and must wait for capacity at doors.
Deeperv = v₀[1 − e^(−1.913(1/ρ − 1/5.4))]; relaxation τ = 0.5 s; 3 passes of overlap resolution; token-bucket doors at 1.33 p/s/m; adult v₀ 1.34 ± 0.15 m/s.
Don't claimThat we model individual psychology, group behaviour (families staying together), or physical crush forces.
Q13Why Dijkstra and not A* or BFS?
SayBFS assumes equal step costs, but our diagonal steps, wall-side penalty and congestion make costs unequal. A* finds one path for one person; we need every cell's distance to every exit, which a multi-source Dijkstra gives in one pass per exit.
Q14How do you detect bottlenecks?
SayWe estimate density per cell with a Gaussian kernel, smooth it over 1 s, and count how long each cell stays above 2.15 people/m² — Fruin's Level of Service F. Connected cells critical for at least 3 s form a zone, named after the nearest door, ranked by duration × peak.
Q15What happens when an exit is blocked?
SayIt becomes a wall; distance maps are recomputed; people re-route to the remaining exits. In our model blocking Door B raises the time from 93.6 to 110.5 s, and the Lobby exit goes unused because Door B was its only access.
Q16How do you handle panic?
SayPanic is a 0–1 slider. Higher panic means up to 30 % faster walking and faster reactions, but less re-routing and door clogging when it's crowded — the "faster-is-slower" effect.
Don't claimThat it is a validated psychological model; it is a simplified, phenomenological version of the effect described by Helbing et al. (2000).
Q17How do you model elderly people and wheelchair users?
SayThey are separate agent types with lower speeds (0.7–1.0 m/s for wheelchairs), larger body size, longer reaction times, and wheelchair users avoid exits marked not step-free. The analysis shows an outcome table per group and warns if wheelchair users are among the last out.
Don't claimStair evacuation chairs or assisted carries in detail — stairs are modelled as slow floor; separate floors are not modelled.
Q18Your peak density is 6 people/m², but the speed curve stops at 5.4. Isn't that inconsistent?
Say5.4 is a parameter of the speed curve — the density at which walking stops. The 6.0 is a smoothed kernel estimate at the tightest point of a queue arch, where people are pressed against the door frame. Both say the same thing: that spot is critical.
DeeperAgents are discs of 0.22 m radius; close packing allows ~6 p/m² locally. We report it as "Critical" rather than as an exact physical measurement.

4AI & 3D modelling

Q19Is the AI assistant connected to a real AI model?
SayYes — Google Gemini, called from our Node server; the panel shows "Connected · Gemini". It receives a snapshot of the real simulation, so its answers use our measured numbers. If no key is configured it switches to a clearly labelled offline guide that is rule-based, not AI.
Don't claimThat we trained or fine-tuned the model, or that the AI runs the simulation — the engine does.
Q20Can the AI change my venue on its own?
SayNo. Any action that changes something shows a Confirm card first, and what-if tests run on a copy, never on the original venue.
Q21How does the 3D model get generated?
SayParametrically, from the same 0.5 m grid the engine uses: walls, seats, stage, doors and exits are extruded into 3D with Three.js. No 3D scanning — so if the blueprint is right, the 3D is right.
Q22Can a single image accurately reconstruct an entire building?
SayNo, and we don't claim that. From photos, the AI gives a first draft — rooms, doors, seating — but a photo can't measure distances. Without measurements every size is marked "unverified", and the user reviews each element. For accuracy, use a floor plan with scale calibration or the measurement-based Quick room builder.
Q23What happens if the floor plan is incorrect?
SayThen the results are wrong — garbage in, garbage out. That's why we have calibration from a known length, validation checks (unconnected doors, unreachable floor, capacity), "dimensions unverified" warnings on every result, and why we position it as a comparison tool.
Q24Is the voice assistant real-time?
SayIt uses the browser's built-in speech recognition and speech synthesis; text answers stream as they are generated. We tested the text assistant live; we haven't tested voice on this laptop's microphone, so we demo with text.
Don't claimReal-time voice conversation or that voice works offline.

5Accuracy & validation

Q25How realistic is your simulation?
SayIt uses published, widely used parameters — Weidmann walking speeds, SFPE door flow, Fruin density levels — so the behaviour is realistic in kind: queues at doors, slowdowns in crowds, re-routing. Absolute times depend on the input and haven't been validated against a drill in this hall yet.
Don't claim"Accurate to the second", "validated", or "as accurate as commercial tools".
Q26How do you validate your results?
SayToday: internal consistency — reproducible seeds, an automated regression test, hand cross-checks such as people ÷ door flow, and three-seed comparisons for every recommendation. Next: compare with a timed mock drill in Hall 406 and with published benchmark cases.
DeeperExample cross-check: Door A carried 84 people; 84 ÷ 1.33 ≈ 63 s of discharge plus 10–30 s reaction ≈ 75–95 s, consistent with the measured 93.6 s.
Q27Why does a result change when I change the seed?
SayThe seed decides who sits where and each person's speed and reaction time. Different crowds give slightly different times — that's real variability. That's why recommendations use three seeds and show the range.
Q28The report shows a door at 1.40 of 1.33 p/s — above capacity?
SayPeak flow is counted in 5-second windows. The door gate can store one "token", so a single window can briefly show slightly more than the average capacity. Over time the flow is limited to 1.33 p/s per metre.

6Scalability & real-world implementation

Q29Can it handle 1,000 or 10,000 people?
SayThe Hall 406 simulator goes up to 400. In Venue Studio, we measured a 30 × 25 m room with about 900 people simulated in 0.6 s of computer time. Around 3,000 people still runs (about 14 s), but a handful of agents didn't finish within the 600 s limit — a known limitation we'd fix before scaling. 10,000 would need optimisation and spatial partitioning.
Don't claimThat it handles 10,000 people in real time today.
Q30Can it model a multi-storey building?
SayNot yet. It models one floor; stairs are treated as slow floor. Multi-floor with stair flow is our first future step.
Q31How would you deploy this for real?
SayIt's already a production build (npm run build) served by a small Node server. Next: host it, add a real database and login, team sharing of venues, and partner with a college for a validation drill.

7Limitations & future scope

Q32Is this a certified life-safety system?
SayNo. It's a comparative planning and decision-support tool. Every result screen says so. Compliance requires a qualified fire-safety engineer and the National Building Code, NBC 2016 Part 4.
Q33What are the current limitations?
SaySingle floor; no fire or smoke spread; simplified panic; no group behaviour; door and walking parameters are planning values; Hall 406 dimensions not yet measured; AI drafts need checking; accounts are local demo accounts. Chapter 15 lists them all.
Q34What happens without internet access?
SayEverything except the AI keeps working — simulator, 3D, recommendations, Venue Studio, reports. Fonts and libraries are bundled locally. Only the AI assistant and AI drafting need internet.
Q35Do you simulate fire and smoke?
SayNot their spread. You can draw fire-seat zones that close an area and smoke zones that slow walking, and the wizard lists clearly what is simulated and what isn't. Coupling a fire model to compute ASET is future work.

8Innovation & impact

Q36Evacuation simulators already exist. What's new here?
SayThree things together: it runs free in a browser for non-specialists; it automatically tests and ranks design changes with fair multi-seed re-simulation instead of only visualising; and it's transparent about every parameter and limitation.
Don't claimThat no other tool can do this, or that it is better than professional software.
Q37Why trust your recommendation over common sense?
SayBecause it's tested, not assumed. Common sense says "widen the worst door". In our hall, widening Door C — the worst bottleneck — saves about 3 s, but adding a west exit saves about 17 s. Each option is re-run on the same three crowds.
Q38What was the hardest technical problem?
SayGetting realistic crowding. Early versions let people overlap, so densities were unrealistic; we added three passes of collision resolution and a Gaussian density estimate. Then the faster-is-slower effect didn't appear because door density was measured on wall cells — we fixed it by measuring in front of each door.
Chapter 15

Limitations

Knowing these by heart is a strength, not a weakness.

Positioning statement — memorise "Simulation outputs are estimates based on model assumptions. They are meant for comparing design options, and need validation against real-world drills and expert review before being used for safety decisions."

15.1What the prototype can do today

  • Simulate 200–400 people in Hall 406 in four scenarios (any combination of crowd size, mobility, reaction time, panic and blocked exits), live in 2D and 3D.
  • Measure RSET, t50/t95, density, exit use, queuing; detect bottlenecks; produce risk findings.
  • Test and rank design changes with 3-seed re-simulation; show before/after; save and print reports.
  • Build custom single-floor venues from floor plans, DXF, drawing, measurements or AI drafts; configure detailed populations; simulate and analyse them.
  • Explain everything through Learn, How It Works, Technology and the AI assistant.

15.2What it cannot do yet

LimitationDetail
Single floor onlyStairs and ramps are slow floor zones (×0.6 adults, ×0.12 wheelchair users); no multi-storey flow.
No fire / smoke physicsNo fire growth, smoke movement, heat or toxicity, so no ASET. Hazard zones are static.
Simplified behaviourNo families or groups staying together, no helping behaviour, no leaders/followers; caregivers are not kept beside the person they assist.
No physical crush forcesDensities are measured, but forces on bodies are not modelled.
Planning-value parametersWalking speeds, door flow (1.33 p/s/m), reaction times and environment multipliers are literature/planning values, not calibrated to Indian college crowds.
Hall 406 is representativeDimensions not measured on site.
Grid resolution 0.5 mDoor and exit widths are effectively multiples of 0.5 m; very narrow features are approximated.
Large crowds~900 people is fast; at ~3,000 a few agents may not finish within 600 s; 10,000 is untested.
ImportsWall tracing cannot detect doors; DWG not supported; PDF imports page 1 only; DXF supports lines, polylines and arcs.
AINeeds internet and an API key; free tier is rate-limited; drafts from photos are estimates.
Voice and cameraImplemented with browser APIs but not tested on the presentation hardware.
Accounts and storageLocal to one browser; no cloud sync or multi-user sharing; demo authentication only.
Known UI quirk3D View page: Door B label can stay "blocked" after switching scenario via that page's dropdown.

15.3What needs real-world testing

  • A timed mock drill in Hall 406 (video-recorded) to compare total time, per-door counts and queue locations with the model.
  • Measured door flow rates and reaction times for Indian college audiences.
  • On-site measurement of Hall 406 (room, aisles, door clear widths).
  • Usability testing with real venue administrators.

15.4What data would improve accuracy

  • Accurate CAD/DXF plans of real venues.
  • Drill footage → speed, density and door-flow measurements for calibration.
  • Occupancy patterns (where people actually sit), share of mobility-impaired occupants.
  • Alarm and detection timings from the building's fire-alarm system.

Chapter 17

How to run the project

On the presentation laptop, in the project folder.

CommandWhat it does
npm installOnce, to install dependencies (needs internet; already done).
npm run devStarts the development server. Open the URL it prints (usually http://localhost:5173; if that port is busy, Vite uses 5174). Includes the AI endpoint.
npm run test:simRuns the 4 scenarios in Node. Expected RSET: Normal 93.6 · Blocked 110.5 · Larger 164.9 · Mixed 113.9 s.
npm run build then npm startProduction build and server on http://localhost:4173 (also serves the AI endpoint).
npm run illustrationsRegenerates the 7 SVG illustrations from the engine.
AI keyThe file .env.local in the project folder holds GEMINI_API_KEY=… (free key from Google AI Studio). It is read only by the server and never committed or sent to the browser. Restart npm run dev after changing it. Without it, the assistant shows a setup card and the offline guide.
