Scene 2 — Problem statement

1:00
Navya
Evacuation plans today are static drawings with green arrows. They show where to go, but not how long it takes, where the crowd will get stuck, or what happens if one exit is blocked by stored chairs — which happens more often than we like to admit.
Navya
And crowds don't behave like arrows. A one-metre door can let through only about 1.33 people per second. When people arrive faster than that, a queue forms, the crowd gets denser, and in a dense crowd everyone walks slower. Those problems are invisible on paper.
Tishank
Real drills help, but they are rare, they cost time, and you cannot safely test "what if this door is blocked" or "what if we allow 400 people". Professional evacuation software exists, but it is expensive and made for specialists.
Tishank
So colleges, auditoriums and event organisers make decisions about doors, seating and crowd size without any way to measure their effect on safety. That is the gap we are addressing.

0:45

Tishank
EvacPrint does four things: Simulate, predict, optimize, protect. It turns a venue into a grid of half-metre squares, fills it with virtual people, sounds a virtual alarm, and measures what happens. Then it tries design changes by itself and tells you which ones actually help.

Scene 5 — Architecture & tech stack

1:15
OPTIONAL SCREEN: Technology page → Model card.
Navya
EvacPrint is a web app built in plain JavaScript with Vite. The heart is our own simulation engine — about a thousand lines of pure JavaScript with no dependence on the page — so the same code runs the live view, runs in background Web Workers for the recommendations, and runs in Node.js for our automated tests.
Navya
The 3D view uses Three.js, the plan and heatmap use the Canvas API, and charts are SVG. Venues and reports are stored in the browser itself, in IndexedDB and localStorage, so the simulator works fully offline. Only the AI goes through a small Node server, which keeps the API key secret.
Tishank
The engine uses established research. Routes come from Dijkstra's algorithm — we compute a distance map from every exit, and people walk downhill on it; every two seconds crowded areas become more "expensive", so people re-route away from queues. Walking speed follows the Weidmann speed–density curve. Doors follow the SFPE planning value of 1.33 people per second per metre. Density is measured with a Gaussian kernel, and bottlenecks are areas above Fruin's Level of Service F for at least three seconds.
Tishank
Every parameter and its source is listed on our Technology page, and every number on screen comes from a run. Same seed, same result — so anyone can reproduce our numbers.

Scene 6 — Innovation & uniqueness

0:40
Tishank
Three things make EvacPrint different. First, it doesn't just visualise — it recommends, and it tests every recommendation with full re-simulations instead of rules of thumb. That matters: in our hall, the worst bottleneck is at Door C, yet widening Door C saves only about 3 seconds, while a new west exit saves 17. Intuition would pick the wrong fix.
Tishank
Second, one engine drives every view, so the 2D, 3D and report always agree. Third, it is honest: it shows what it simulates and what it doesn't, marks unverified dimensions, and says on every result that it is a planning estimate — so weaknesses are found before an emergency, not during one.

Scene 7 — Practical applications & future scope

0:40
Navya
Today, EvacPrint can already help colleges and schools check seminar halls and labs, auditoriums and event organisers decide crowd limits and seating, and offices or public buildings test what a blocked exit costs. Hospitals and malls are natural next users, but they need features we haven't built yet.
Navya
Our next steps are multi-floor buildings with stairs, validation against real mock drills, fire and smoke spread coupled to the evacuation, and live occupancy data from sensors — so the digital twin stays in step with the real building.
